# AdSense 审核诊断参考

本文件整理 AdSense 审核实践经验和社区反馈，供 `seo-code-diagnostic` 在处理 AdSense review、low value content、policy、游戏站/工具站审核失败时使用。

核心判断：AdSense 审核本质上是在判断“这个网站是否值得展示广告”。对游戏站和工具站来说，风险常常不是技术 SEO 某一项缺失，而是整个站点看起来像自动生成的低质套壳。

## 1. 反复被拒后的有效改进方向

一个站点从 2 月开始连续 6 次申请 AdSense review，前 5 次常见反馈是 low value 或 policy，第 6 次才通过。经验归纳：

- 网站要有视觉特色。即使基于模板，也要让配色、字体、图片和页面氛围与主打游戏/工具相关。
- 套壳不能只是套壳。游戏站不能只有 iframe，工具站不能只有入口，要基于关键词解决相关问题或提供可读内容。
- 不要浪费长尾词。小站的长尾页面可能长期产生被动收入，一个能稳定产生收入的网站有复利价值。

诊断时要把 AdSense 当成“内容站可信度 + 原创价值 + 政策安全 + 基础 SEO”的综合审核，不要只查 TDK。

## 2. Low value content 常见含义

社区反馈里，low value content 通常指这些情况：

- 页面太薄，没有原创内容，只有产品营销、工具入口、游戏 iframe 或卡片列表。
- 没有 Blog、Guides、Tutorials 等内容区，Google 难以判断站点持续提供价值。
- 页面没有收录、没有流量或几乎没有用户信号。流量不一定是官方硬门槛，但近年审核更看重站点是否真的被用户找到。
- 首页像产品宣传页，不像内容发布站。需要补充信息、教程、指南、FAQ 和相关内容入口。

输出时可以说“这会增加 low value content 风险”，不要说“Google 一定因为这个拒绝”。

## 3. 游戏站/工具站审核清单

### 视觉风格

网站要有明显设计风格，不能一眼像通用模板。最简单的方法是参考主打游戏或工具主题：

- 游戏站：使用游戏本身的配色、字体、角色/场景氛围和视觉节奏。
- 工具站：使用一致的品牌色、清晰的产品截图/状态、可信的排版和真实使用场景。

审核官打开第一眼应能感到“这是为这个主题认真做的网站”，而不是批量生成的壳。

### 内容质量

纯 iframe 不是内容。每个游戏页至少需要：

- 原创游戏介绍；
- 玩法说明；
- 常见问题；
- 相关游戏/攻略/技巧链接；
- 必要时提供操作技巧、关卡建议、替代玩法或背景信息。

工具页至少需要：

- 工具解决什么问题；
- 适合谁用；
- 使用步骤；
- 输入/输出说明；
- 例子、限制和 FAQ；
- 相关工具或相关教程。

首页和分类页也要有文字说明，不能只是一堆封面图或按钮。

### Blog / Guides

审核阶段建议准备 5-10 篇质量不错的原创文章。主题可以围绕：

- 游戏攻略、玩法技巧、关卡策略；
- 同类型游戏推荐；
- 工具使用教程、问题解答；
- 行业资讯或用户场景；
- 长尾关键词对应的专题页面。

Blog 的作用有两个：给审核者看到持续原创内容，也给搜索引擎更多可收录页面。

### 必备页面

以下页面要齐全，并从导航或页脚可访问：

- About：网站做什么、谁在维护、服务什么用户；
- Contact：联系方式，邮箱即可；
- Privacy Policy：隐私政策，要匹配 cookies、广告、统计、表单等真实行为；
- Terms of Service：使用条款和免责声明。

Privacy Policy 和 Terms 可以用工具生成初稿，但必须和网站实际情况一致。

### 内容红线

以下内容需要人工确认，不能只靠代码扫描：

- 未授权的版权游戏、角色、图片、音频、商标；
- 成人内容；
- 赌博相关内容；
- 仇恨、暴力、违法或危险内容；
- 用户生成内容中的政策风险；
- 外链是否导向高风险站点。

这些风险可能直接导致拒绝，严重时可能影响账号。

## 4. GSC 和长尾词优化

如果用户提供 Google Search Console 数据，优先找这些机会：

- 查询排名在 5-20；
- impressions 不低但点击少；
- 页面已经与该查询相关，但内容没有专门覆盖；
- 搜索意图明确，能通过补一节内容或新增页面满足。

从第 12 名推到第 5 名通常比从第 50 名推到首页容易。对游戏/工具站，可以围绕玩法、替代方案、教程、问题、比较、关键词变体做长尾页面。

## 5. 诊断输出原则

AdSense 诊断要先给结论，再给证据：

- 当前更像认真维护的内容站，还是薄内容套壳；
- 哪些问题是代码能证明的；
- 哪些问题必须人工确认；
- 哪些改动最可能降低 low value / policy 风险；
- 提交前还缺哪些数据。

不要承诺“改完一定通过”。可以说“这些改动会降低被 low value content 或 policy 拒绝的风险”。
